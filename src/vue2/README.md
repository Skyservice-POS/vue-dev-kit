# Vue 2-збірка — тимчасовий міст

> **Не видаляти без прочитання цього файлу.** Цей шар уже видаляли одного разу
> (`14b0fbb`, v2.0.0) з формулюванням «незрозуміло, для чого». Тепер причина є,
> і вона записана нижче разом з умовою зняття.

## Навіщо існує

Адмінка Skyservice POS (`skyservice-dashboard-vue`) — Vue 2 і сидить на BootstrapVue.
BootstrapVue не має версії під Vue 3 і не матиме, тож перейти на Vue 3 можна лише
знявши його. Але заміна — цей кіт — сама по собі Vue 3.

Замок розчіпляється так: **мігрується контракт, а не рантайм**. Адмінка переїжджає
на API кіта, ще будучи на Vue 2 — через цю збірку. Коли жодного `b-*` не лишиться,
вмикається `@vue/compat`, і той самий PR замінює підшлях імпорту:

```diff
- from '@skyservice-developers/vue-dev-kit/vue2'
+ from '@skyservice-developers/vue-dev-kit'
```

Уся ризикована робота розбивається на дрібні кроки, які їдуть у прод окремо.
Фліп-день лишається механічним.

## Що це насправді

**Адаптери, а не реалізації.** Кожен компонент тут — обгортка над форком
BootstrapVue, що перекладає контракт кіта на пропи `b-*`:

```vue
<b-button :variant="bsVariant" :size="bsSize" :disabled="disabled || loading">
  <slot />
</b-button>
```

Десятки рядків замість сотень, а під капотом — реалізація, перевірена роками
в проді. Тому переїзд адмінки на цю збірку має **близький до нуля поведінковий
ризик**: поведінка не «схожа», вона та сама.

> **Чому не просто реекспортувати BootstrapVue?** Тоді місцям виклику не було б
> на що мігрувати — `<b-button variant="info">` лишився б як є. А у фліп-день
> Vue 3-компоненти мусили б прийняти API BootstrapVue назавжди, і тридцять
> міні-застосунків успадкували б чужий API 2016 року.

## Використання

```js
// npm i bootstrap-vue@github:vladkvlchk/bootstrap-vue-fork#master
import Vue from 'vue';
import SkyKit, { SkyButton, SkyInput } from '@skyservice-developers/vue-dev-kit/vue2';

Vue.use(SkyKit);            // глобальна реєстрація всіх компонентів і директив
// або точково:
export default { components: { SkyButton, SkyInput } };
```

`vue` і `bootstrap-vue` — зовнішні залежності, їх дає споживач. Для `bootstrap-vue`
це принципово: адмінка вже має його у себе, і другий екземпляр у бандлі означав би
два незалежні реєстри компонентів.

**Стилів ця збірка не постачає** — вигляд дає Bootstrap CSS, який у споживача вже
підключений. Тому підшляху `./vue2/style.css` немає, на відміну від Vue 3-збірки.

## Межі

- **Фрагментів у Vue 2 немає.** `SkyInput` і `SkySelect` у Vue 3 — фрагменти
  (`<input>` + `<small>` з підказкою). Тут без `hint` віддається голе поле, а
  обгортка зʼявляється лише коли `hint` заданий — щоб не зсунути верстку там,
  де її не було.
- **Розмітка відрізняється від Vue 3-версії.** Це очікувано: адаптер віддає DOM
  BootstrapVue, Vue 3-компонент — власний. Розбіжності звіряються звітом DOM-діфу
  (див. issue #52), а не тестами.
- **Форм-контроли емітять `input` на додачу до `update:modelValue`.** Це свідоме
  відхилення від задекларованого Vue 3-контракту, і його треба внести до
  allowlist паритет-чека. Причина: у Vue 3 коренем `SkyInput` є сам `<input>`,
  тож `@input` там працює через нативний fallthrough — а у Vue 2 з
  `inheritAttrs: false` не працював би. Без цього кожен `@input` на місцях
  виклику довелося б переписувати на `@update:modelValue`, а таких сотні.
- **Частина пропів приймається заради паритету контракту, але не діє** —
  наприклад `showIcon` у `SkyAlert` і `dot` у `SkyBadge`: у BootstrapVue таких
  елементів немає. Це задокументовано в самих компонентах.

## Умова видалення

Цей шар знімається, коли в `skyservice-dashboard-vue` не лишиться жодного
імпорту `@skyservice-developers/vue-dev-kit/vue2`.

Перевірка:

```bash
grep -r "vue-dev-kit/vue2" src/    # порожньо → шар можна видаляти
```

Разом із ним знімаються: `vite.vue2.config.js`, підшлях `./vue2` в `exports`,
`bootstrap-vue` з `peerDependencies` і devDeps `@vitejs/plugin-vue2` /
`vue-template-compiler`.

До того моменту шар у режимі підтримки: нових можливостей сюди не додаємо,
лише те, що потрібно адмінці для переїзду.
